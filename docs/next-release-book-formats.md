# Next release: native book formats and fonts

## Requirements

- Open FB2 directly from its original file. Do not publish a sibling EPUB, hide/rename the FB2, or redirect Recent Books to another file.
- Preserve FB2 presentation semantics supported by the reader: section hierarchy and heading levels, paragraphs/poetry, emphasis/strong/superscript/subscript, links and footnotes, images, metadata, and Cyrillic/legacy encodings. Keep the source immutable. Persist progress against the FB2 path.
- Keep EPUB behavior and its cache/progress/sync flow unchanged.
- Audit MOBI/AZW instead of claiming compatibility: the current reader dispatches to EPUB, XTC, Markdown and TXT readers; current source has no MOBI/AZW parser or reader. New support must be DRM-free only, never attempt DRM circumvention, and should preserve images, links, headings, metadata and reading position. Define explicit graceful errors for unsupported/encrypted variants.
- Keep the existing TTF/OTF-to-CPFont Font Manager path. It already has a browser Web Worker converter backed by the checked-in FreeType WASM + CPFont writer, with parity tests against the Python converter. Validate it during this release and ensure format work does not regress it. Where books embed fonts, expose/convert only fonts permitted by the book's license and provide a clear unsupported-font error.

## Baseline findings from the initial audit (historical)

`ReaderActivity::onEnter()` currently intercepts `.fb2`, displays `FB2 -> EPUB...`, calls `Fb2Converter::convert()`, relocates the Recent Books record, then launches the EPUB reader. `docs/dev-fb2-publishing.md` documents a sibling EPUB and a reversible dot-prefix rename of the FB2. This is the behavior to replace for direct FB2 opening; keep any optional/manual publishing tool separate from opening.

The library recognizes `.fb2`; `ReaderActivity` has no direct FB2 reader. `FileBrowserModel` recognizes EPUB/XTC/TXT/Markdown plus FB2, but no `.mobi` or `.azw`. No MOBI/AZW parser is present in `src`/`lib`. Do not describe either Kindle format as currently available.

Font conversion exists in `src/network/html/FontsPage.html`, `src/network/html/js/font-converter.js`, and `tools/ftwasm`. Its documented output is byte-identical to the Python CPFont converter and includes OTF test coverage; this release must rerun its host parity/smoke checks and exercise the Font Manager upload endpoint.

## Implementation and acceptance gates

1. Parse FB2 into a private renderer cache under `/.crosspoint/tmp/fb2-reader-v3-*` and pass its XHTML sections through the existing pagination/settings/progress machinery. Group per-book generated caches under `/.crosspoint/tmp/`, keeping each format and source book in a distinct subfolder; migrate existing cache folders intact on first use. The source remains at its original path and is not renamed; no sibling EPUB is created. Keep XML parsing incremental and bound images/IDs/chapters to avoid ESP32 heap spikes.
2. Add host fixtures covering UTF-8 and Windows-1251, nested headings, emphasis, poem/stanza/verse, notes, links, embedded JPEG/PNG, malformed XML, large input and duplicate IDs. Assert source bytes and path are unchanged after opening and closing. Add a QEMU check that opens FB2 from the library, pages, returns, and resumes at the saved location without an EPUB artifact.
3. Decide the Kindle implementation only after checking flash/RAM headroom, format and license constraints. A parser must feed the reader directly or use an explicitly named, user-visible cache that does not alter/remove the source; no silent conversion that claims native support. Include separate MOBI7, AZW, AZW3/KF8 and encrypted-file test cases and state supported subset precisely.
4. Run the existing EPUB regression suite, the full Font Manager TTF/OTF parity/smoke suite, X4 Pro build, and QEMU tests. Update release notes and CHM only after accepted behavior is demonstrated.

## MOBI/AZW library feasibility
- `libmobi` is now vendored from upstream 0.12 under LGPL-3.0-or-later, with the license retained. A `MOBIStream` random-access adapter replaces the `FILE*` requirement for reads; a `MobiBook` RAII wrapper opens the original SD file read-only and rejects encrypted inputs. The parser and wrapper compile in the X4 Pro build. A native host smoke parsed upstream `sample-textread.mobi` (154,544 bytes) into one 95,604-byte HTML flow and returned `MOBI_FILE_ENCRYPTED` for upstream `sample-drm-v1.mobi` (86,580 bytes). An isolated Xtensa link retained the parser entrypoints at 111,679 bytes text, 328 data, 336 bss. However, no reader path calls `MobiBook`, so the final app still does not open MOBI/AZW; the firmware image metrics remain at 6,256,133 app bytes / 6,553,600 and 111,296 RAM bytes. More importantly, libmobi loads records and reconstructed RawML into heap; the source is not yet bounded-memory for large books. No EPUB pipeline, content pagination, image/style fidelity, AZW3/KF8/hybrid fixture, or resume behavior has been integrated or tested. Do not claim support until these are addressed.
- Encrypted books will be reported unsupported; do not use any DRM removal or circumvention path.

### MOBI7 resource-link correction
- The native sample exposed an upstream reconstruction bug: KF7 resource references carry list ordinals, but the parser looked up a MOBIPart by PDB record UID. The generated HTML therefore used .dat for a resource whose parsed type was BMP. The lookup now resolves by resource-list ordinal; the same fixture now emits `resource00000.bmp`. The original and reconstructed `src` attributes remain duplicated, so the direct-MOBI path still needs link normalization before the existing HTML visitor can consume it reliably.

### MOBI markup normalizer prototype
- Added a streaming `src`-attribute normalizer with a sink callback, preserving all bytes except earlier duplicate `src` attributes and keeping the final reconstructed resource URI. It uses constant auxiliary memory and leaves unrelated markup untouched.
- Four focused Windows/MSVC tests pass: reconstructed duplicate URI wins, single/unrelated attributes including quoted `>` remain intact, comments/multiple duplicates are handled, and sink errors propagate. The helper is not connected to the MOBI reader yet; flow-part boundaries, assets/styles, page integration, and memory behavior remain open. This is a tested parser utility, not MOBI/AZW reading support.
